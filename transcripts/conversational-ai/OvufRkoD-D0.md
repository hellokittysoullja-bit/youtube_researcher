The interviewer asks you to design a URL shortener. Many candidates immediately start. We need a load balancer, web servers, radis for caching, and a hash function for 

[01:31] generating short URLs. This is wrong. You're designing a system without understanding the requirements. Different URL shorteners have vastly different needs. The fakes start with questions. Always ask about functional requirements. What features do we need? 

[02:01] Who are the users? What's the expected usage pattern? Ask about non-functional requirements. How many URLs per day? What's the readto write ratio? Any latency requirements. Document your assumptions. If the interviewers doesn't specify something, state your assumption clearly. This shows you understand the system design is about solving real problems. But asking the right questions is only the beginning. A third mistake happens when you start designing. You're designing a video streaming service. 

[02:33] Requirements are clear. The candidate immediately discusses video encoding formats, CDN configurations, and compression algorithms. This is backwards. You are diving into implementation details before establishing the overall architecture. The fakes start with the big picture. Begin with major components. We need an upload service for content creators, a processing service for video encoding, storage for video files, and a streaming service for viewers. Show the 

[03:05] relationships. User uploads through our API. Videos get ceued for processing. Processed video go to distributor storage and streaming happens through a CDN. Walk through the flow. Websocket provides real-time communication with minimal overhead but require handling persistent connections and is more
