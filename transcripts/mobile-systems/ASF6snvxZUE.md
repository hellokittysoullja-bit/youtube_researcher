# WebSockets at Scale: System Design

[00:00] Imagine this, Bitcoin just smashed its all-time high. The market goes completely crazy. In a matter of seconds, 5 million users open your crypto trading app. They all want to see the live price ticker, and they all want to smash the buy button at the exact same time. If you built your system like a standard crowd application, your servers are already dead. Then, in system design interviews, people throw the word web sockets on the whiteboard like it's a magic wand that solves real-time communication. But here is the brutal 

[00:32] reality. Maintaining millions of persistent TCP connections will absolutely melt your infrastructure if you don't understand the bare metal limits and the load balancer traps. Today, we are not going to write a basic 10-line Node.js web socket chat. We are going to design a distributed, highly available web socket architecture that can handle millions of concurrent users during a massive traffic spike without dropping a single order. Before we scale anything, we need to 

[01:03] make sure we are actually using the right protocol. And this is where most engineers fail the interview right out of the gate. Let's eliminate the wrong choices first. Short polling, where the client asks the server, is there a new price every single second, is a joke at this scale. The HTTP overhead alone will act as a denial of service attack on your own network. WebRTC is peer-to-peer and meant for heavy media streams like video calls. So, that's overkill. This leaves us with 

[01:33] a real engineering choice, server-sent events versus web sockets. Here is the secret. If you are only building a live price ticker where data flows purely from the server to the client, server-sent events is actually superior. It runs over standard HTTP, respects traditional load balancers, and has built-in reconnection logic. But, because our users also need to execute trades, which requires low-latency bidirectional communication, we must choose WebSockets. However, just 

[02:04] remember, WebSockets are stateful, and state is the enemy of scalability. Now, let's talk about hardware. You often read blog posts claiming a single server can hold 1 million WebSocket connections. While theoretically possible, it will not happen out of the box. To achieve this, you have to fight the operating system. First, you run into the file descriptor limit. In Linux, everything is a file, including a network socket. By default, 

[02:35] most Linux distributions cap the number of open file descriptors to a few thousand per process. If you hit 65,000 connections, the OS will silently drop new requests. You must actively tune the kernel parameters, specifically the fs.file-max setting, to at least allow the OS to hold millions of sockets. Second, there is the RAM ceiling. Every open WebSocket connection consumes memory, even when it's doing absolutely nothing. Depending on your language, whether it's Python, Node.js, or Java, 

[03:07] the OS needs to allocate read and write buffers for that TCP stream. A conservative estimate is about 50 kilobytes per idle connection. 1 million connections means 50 GB of RAM are gone, just to hold the sockets open. And if you are using secure WebSockets over TLS, which you absolutely must in finance, those cryptographic buffers can easily double that memory footprint. You don't want a single server holding a million connections anyway. If that one machine goes down, a million clients 

[03:37] will instantly try to reconnect, creating a thundering herd that will take down your entire system. You must scale horizontally. And that brings us to the biggest nightmare of all, load balancing long-lived connections. Now that you know you need to scale horizontally across multiple servers, how do you distribute the incoming traffic? You put a load balancer in front of them. Easy, right? Well, if you use a standard application load balancer, a layer 7 proxy like an AWS ALB or a default engine X setup, you're 

[04:09] walking right into a trap. Layer 7 load balancers operate at the application layer. They parse the HTTP headers, terminate the TLS connection, and wait for requests. But WebSockets are not standard HTTP. They start as HTTP, but they transform to a long-lived TCP connection. If a user is just sitting there watching the crypto charts and not sending data for 60 seconds, a layer 7 proxy will often hit an idle timeout and silently 

[04:39] drop the connection. Now, multiply that by a million users. When your load balancer drops those connections, a million apps will instantly try to reconnect at the exact same millisecond. This creates a self-inflicted denial of service attack that will crash your authentication services. To fix this, you must drop down to layer 4 load balancing using a network load balancer or HAProxy in raw TCP mode. Layer 4 doesn't care about HTTP headers 

[05:10] or application logic. It routes purely based on IP addresses and ports at the transport layer. It acts as a dumb, hyper-fast pipeline that passes the raw TCP stream straight through to your servers. It uses almost no memory or CPU per connection, meaning it can easily hold open millions of persistent connections without breaking a sweat or enforcing aggressive idle timeouts. All right. So, our layer 4 load balancer 

[05:40] is routing TCP streams to our servers. But what do those back-end servers actually look like? If you put your business logic, like executing trades, checking balances, and processing order books on the exact same server that holds the WebSocket connections, you've made a massive architectural error. Every time you deploy a bug fix or code update to your business logic, you have to restart the server. Restarting a server that holds 100,000 WebSockets means dropping 100,000 connections. Instead, you must use the gateway 

[06:12] pattern. You separate your cluster into dumb gateways and smart workers. The gateway servers do absolutely nothing but hold the TCP connection open, handle TLS decryption, and pass lightweight messages back and forth. They rarely change, meaning they almost never need a restart. The smart workers handle the actual crypto trading logic and can be scaled up, down, or restarted independently without ever dropping a single user's socket connection. But this decoupling introduces a brand 

[06:43] new problem. Connection routing. Let's say Bitcoin crashes and a smart worker processes a custom price alert for user 99. The worker needs to push this notification to user 99's phone instantly, but we have 50 different gateway servers. How does the worker know which specific gateway server is holding the TCP socket for user 99? You need a distributed session manager. Every time a user connects to a gateway node, that node writes a record to a 

[07:13] highly available distributed key-value store, like a Redis cluster or a DHT. User 99 is connected to gateway number four. Now, when any backend service needs to send a private message to a user, it checks the session manager, finds the correct gateway IP, and sends a fast internal RPC message to that specific gateway. The gateway then pushes it down the open WebSocket. By decoupling the socket management from the business logic, and by using L4 load 

[07:44] balancing for raw TCP passthrough and tracking state in a centralized routing table, you've built a system that can scale out infinitely. In a crypto exchange, the biggest challenge isn't private messages, it's the global broadcast. When the Bitcoin price changes, which happens hundreds of times a second, that single price update needs to be blasted out to millions of connected users instantly. The standard tutorial answer is to use Redis pub/sub 

[08:14] as a message backplane. The trading engine publishes the price to a Redis channel, and all 500 gateway servers subscribe to that channel. For small to medium scale, this is perfect, but at massive scale, you hit the fan out problem. Redis is single-threaded. If it has to duplicate and push thousands of price ticks per second to hundreds of subscribers, it becomes entirely CPU bound. Redis goes from being your fast cache to your biggest bottleneck. To survive this, enterprise systems move away from a pure 

[08:44] push-based Redis backplane to a distributed event streaming platform like Apache Kafka or a lightweight high-throughput messaging mesh like NATS. Instead of the broker burning CPU trying to push messages to everyone, the gateway servers independently consume from partitioned Kafka topics. This decouples the trading engine's throughput from the number of connected users, allowing the backplane to scale horizontally. Now, let's talk about the most overlooked edge case in WebSocket 

[09:16] design, the real world. Mobile networks are terrible. A user drives into a tunnel, their 4G drops for 3 seconds, and the TCP connection breaks. When they drive out of the tunnel, the app automatically reconnects. But what happened during those 3 seconds? They might have missed a critical price alert or an order execution notification. The naive approach is to have the client reconnect and query the main database. Fetch all my notifications for the last 5 seconds. Do not do this. If a server 

[09:47] blip causes 100,000 users to disconnect and reconnect simultaneously, 100,000 heavy database queries will hit your primary DB at the exact same time. This is called a thundering herd and it will take your entire system offline. The solution is sequence IDs and an in-memory ring buffer. Every single message sent over the websocket must have a strictly incrementing sequence ID. The client keeps track of the highest ID it has received. When it 

[10:19] reconnects, it doesn't query the database. It sends a lightweight payload to the gateway. I am reconnecting. My last seen ID is 1042. The backend maintains a small, fast ring buffer, maybe in Redis, holding only the last 100 messages for that user. It instantly replies with messages 1043 and beyond. You guarantee message ordering, you prevent data loss, and your main database doesn't even notice.

Decouple your architecture using the gateway pattern, so your business logic doesn't crash your sockets. Track your users with a distributed session manager
